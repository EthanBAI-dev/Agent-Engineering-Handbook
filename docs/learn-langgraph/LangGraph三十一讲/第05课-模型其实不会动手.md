# 模型其实不会动手：自己写一遍最小的 agent

> **导读：** 一件事要分好几步才做得完，怎么让程序自己一步接一步做下去？
> 这一讲先不用任何现成工具，就用一个最普通的「反复做」把它写出来，只要几十行。
> 读完你能说清楚这几十行为什么够用，以及它在哪四个地方会顶到天花板。

大模型就是 ChatGPT、DeepSeek 那类会聊天的程序。
上一讲你已经能让它决定「这件事要不要借助一个现成的小程序来做」了。

**但它做完一次就停了。** 你问一句，它做一步，结束。

真正的活儿往往要连做好几步：先算这个，拿到结果再算那个，最后才得出答案。
这一讲就让它反复做，直到做完。

> **这一讲是特意绕开现成工具的。** 先自己写一遍，你才知道下一讲那套现成的东西
> 到底替你做了什么。写完你会顶到四个天花板——它们就是后面二十几讲要一个个拆掉的。

## 先破一个错觉：大模型不会动手

很多人以为大模型是这样工作的：你让它算个数，它就去算了。

**不是。它一根手指头都动不了。**

它能做的只有一件事：**回你一句话。** 那句话可能是普通文字，也可能是一句
「请帮我调 `add` 这个工具，参数是 3 和 4」。

这句「请帮我调……」就是上一讲说的**工具调用**——**模型不自己动手，
它只是提了个要求。真正去调工具的，从头到尾都是你写的代码。**

**所以呢？** 意味着所谓 agent，本质上是你和模型在轮流说话：

| 谁 | 说什么 |
| --- | --- |
| 模型 | 「请帮我调 add，参数 3 和 4」 |
| **你的代码** | 真的去调 `add(3, 4)`，拿到 7，告诉模型「结果是 7」 |
| 模型 | 「请帮我调 multiply，参数 7 和 2」 |
| **你的代码** | 真的去调，拿到 14，告诉它 |
| …… | 一直轮到模型不再提要求 |
| 模型 | 「结果是 2.8。」 |

**这张表就是 agent 的全部。** 剩下的都是工程细节。

## 那循环长什么样

把上面那张表翻译成代码，就是五步：

```python
messages = [系统设定, 用户的问题]

while True:
    ai = model.invoke(messages)      # ① 把当前对话交给模型
    messages.append(ai)              # ② 把模型这句话记下来

    if not ai.tool_calls:            # ③ 它没提要求，说明给出答案了，收工
        return messages

    for call in ai.tool_calls:       # ④ 它提了要求，那就由你的代码去调
        result = TOOLS[call["name"]](**call["args"])
        messages.append(             # ⑤ 把结果塞回对话，回到 ①
            ToolMessage(content=str(result), tool_call_id=call["id"])
        )
```

**注意第 ⑤ 步：工具结果不是直接给用户看的，是塞回对话里给模型看的。**
模型下一轮才能读到「刚才那步算出来是 7」，然后接着往下推。

`messages` 就是那份不断变长的对话记录。**它从头到尾只有这一份，
每一轮都整个送给模型。** 记住这句，后面第一堵墙就是从这儿来的。

`while True` 是唯一的「反复」机制。**跳出的条件只有一个：模型不再提要求。**

```
[调用工具] multiply({'a': 7, 'b': 2}) -> 14
[调用工具] divide({'a': 14, 'b': 5}) -> 2.8

```

一个问题，模型和你的代码来回了四轮，连着调了三次工具，最后给出答案。

**9 条消息是怎么来的？** 系统设定 1 条 + 用户问题 1 条 + 模型说话 4 条 + 工具结果 3 条。
**所以呢？** 一次三步的任务，对话记录就长到了 9 条——**任务每多一步，这个列表就多两条，
而且每一轮都要整个重发给模型。** 这是下面第一堵墙的伏笔。

## 第一堵墙：对话只会变长，没人管

上面算术的例子，工具返回的是 `7`、`14` 这种小数字，看不出问题。

**真实的工具不是这样。** 查一次数据库、调一次接口、读一个网页，返回的都是一大坨。
脚本里模拟了这种情况：

```
== 实验二：工具返回一大坨时，对话是怎么涨的 ==
第 1 轮送进模型：2 条消息，27 个字
第 2 轮送进模型：4 条消息，607 个字
第 3 轮送进模型：6 条消息，1187 个字
第 4 轮送进模型：8 条消息，1767 个字
```

**每查一次，对话就涨约 580 个字。查三次，从 27 涨到 1767，是原来的 65 倍。**

**所以呢？** 三点后果，一个比一个疼：

**第一，钱。** 每一轮都把整份对话重发一次。第 4 轮你为前三轮的内容又付了一遍费。
轮数越多，重复付费越狠。

**第二，慢。** 送进去的字越多，模型回话越慢。

**第三，到某个点它会直接报错。** 模型一次能读多少字是有上限的，超过就拒绝服务。
**查十个城市，这个循环就跑不完了——不是逻辑写错，是撑爆了。**

**你的循环里没有任何一行代码在管这件事。** 它只会往 `messages` 里加，从不拿掉。

> 怎么把对话裁短、又不丢掉关键信息，是第 12 讲的事。

## 第二堵墙：崩在半路，前面全白跑

把第三个工具改成会报错的，跑一下：

```
== 实验三：第三个工具报错，前面两次白跑 ==
[调用工具] add({'a': 3, 'b': 4}) -> 7
[调用工具] multiply({'a': 7, 'b': 2}) -> 14
[崩了] 除法服务连不上
```

`add` 和 `multiply` 都成功了，结果好好地待在 `messages` 里。

**然后进程一退，这些全没了。**

**所以呢？** 算术这个例子无所谓，重跑两次也就几毫秒。但换成真实场景——
前两步花了两分钟、调了三次付费接口、写了半个文件——**第三步一崩，那两分钟和那些钱
全部作废，只能从第一步重来。**

**你的循环里没有任何地方在存东西。** 全部中间结果只活在一个内存变量里。

> 怎么让每一步都存下来、崩了能接着跑，是第 07 讲的事。

## 第三堵墙：这一轮结束，它就把你忘了

`run_agent` 跑完返回 `messages`，函数一结束，这个列表就没人用了。

用户再问一句，你只能重新建一个空列表，从系统设定开始重来。

**所以呢？** 用户说「刚才那个结果再除以 2」，模型会一脸茫然地问「哪个结果？」
——因为它这一轮拿到的对话里，压根没有上一轮的内容。

要修也不是不行：你可以在函数外面搞个字典，用用户 id 当键，把 `messages` 存进去。
**但接着你就要自己处理：多个用户怎么隔离、服务重启后怎么恢复、
两个请求同时改同一份记录怎么办。** 这些都是你要写的代码。

> 怎么让对话记录自动存好、按会话隔开，是第 07 讲的事。

## 第四堵墙：想在动手前问你一句，没地方插

假设 `divide` 换成「删文件」这种危险操作，你想在真删之前先问一句「确定吗」。

在这个循环里，你只能在第 ④ 步前面塞一行 `input()`。

**问题是：`input()` 会把整个程序卡在那儿等。** 这在你自己电脑上跑还行，
一旦跑成网页服务就完全不成立——**总不能让服务器停在那儿，等一个可能三天后才回来的人。**

真正需要的是：**程序停下来、把当前进度整个存好、进程可以退出；
人三天后回来批准，再从当时停的那一步接着往下跑。**

**这件事在这个循环里做不到。** 因为「当前进度」只存在于 `messages` 这个内存变量里，
进程一退就没了——**又回到第二堵墙。**

> 怎么停下来等人、之后原地续上，是第 16 讲的事。

## 动手：让这四堵墙里的两堵变得更明显

脚本里的模型是**按剧本回话的假模型**——每次结果一样，不用钥匙，不花钱。
剧本在 `SCRIPT` 那个列表里，改它就能改模型的行为。

**第一题：让任务变长，看对话涨到多少。**

把实验二的 `lookup_script` 改成查六个城市：

```python
lookup_script = [
    ("tool", "lookup", {"city": c}) for c in ["北京", "上海", "广州", "深圳", "杭州", "成都"]
] + [("final", "六个城市都查到了。")]
```

**验收标准：跑完是 7 轮，最后一轮送进模型 14 条消息、3507 个字。**

对照三个城市时的 4 轮 1767 字——**城市数翻一倍，要送给模型的字数也翻了一倍。
每多查一个城市，就固定多 580 字，而且这些字在后面每一轮都要重发一遍。**

**第二题：让它绕不出来。**

把剧本改成永远返回工具调用，一句 `final` 都不给：

```python
SCRIPT = [("tool", "add", {"a": 1, "b": 1})]
```

因为剧本用完会一直重复最后一项，模型就永远在提要求。

**跑起来会怎样？程序会一直转，不停不下来。** 按 `Ctrl + C` 打断它。

**这是第五个问题，也是这个手写循环最危险的一点：`while True` 没有任何上限。**
模型只要一直提要求，你的程序就一直转，一直花钱。

> 下一讲的框架版本自带一个上限兜底，跑到一定步数会主动报错停下。

## 两个会改变结果的细节

**第一，假模型和真模型的区别只有一处。**
`FakeToolCallingModel` 对外的样子和真模型完全一样——都有 `invoke(messages)`，
都返回一条带工具调用或带文字的消息。**所以那 19 行循环一个字都不用改，
把假模型换成真模型只改一行。**

但要知道：**真模型每次跑出来可能不一样。** 它可能一次提两个要求，
可能顺序跟你想的不同，也可能干脆不调工具直接瞎答。
假模型每次结果固定，是为了让你先把循环本身看清楚。

**第二，本讲代码在 Python 3.11 与 langchain-core 1.x 上跑通。**
只用到消息类型，没用到任何图框架。

## 这一讲得到了什么，下一讲接着讲什么

你手写了一个 agent，**19 行**，能连续调工具、自己判断什么时候收工。
更重要的是你现在知道了：**模型只会提要求，所有实际动作都是你的代码做的。**

但这 19 行撞上了四堵墙：**对话只会变长没人管、崩在半路前面全白跑、
一轮结束就失忆、想让人插手没地方插。** 再加上 `while True` 没有上限。

这五个问题有个共同点——**它们全都是因为「进度」只活在一个内存变量里。**
你没法存它、没法恢复它、没法在中途查看或修改它。

下一讲先解决最外面那层：**同样这个循环，交给框架来写，它会长什么样，
以及那个防止无限转下去的上限藏在哪。**
