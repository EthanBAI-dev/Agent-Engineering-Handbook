# 配图与互动 UI 规范

> 课程正文是内容的唯一来源。图和交互的需求**写在正文里它该出现的位置**，
> 不另开一份需求文档——需求和它要解释的那段话分开放，两边一定会走散。

## 原则

**图只承担文字难以同时表达的东西**：流程、状态变化、职责边界、时间顺序。
一段话能说清楚的，不要配图；配了图也不会有人多看一眼。

判断一张图值不值得做，问三个问题：

1. 去掉它，这段话还读得懂吗？读得懂就不要做。
2. 它是不是在重复正文已经说过的话？是就不要做。
3. 读者看完图，能不能回答一个看文字答不出的问题？答不出就说明图没做对。

**交互要有明确的通过条件**。「点着玩」不是实验。每个互动都要能回答：用户做什么、
屏幕上变什么、怎样算做对了。

## 正文里怎么写

两种区块，都用引用块，GitHub 和网站上都能正常显示。

### 配图

```markdown
> **配图 F01-2｜State 的三个字段**
> **形式**：静态示意图 · `assets/lessons/01-state-fields.svg`
> **画什么**：一个方框列出三个字段，`topic` 和 `count` 标「覆盖」，`log` 标「累加」。
> **必须标注**：三个字段名；两种更新方式的对比。
> **不要出现**：数据库图标、模型头像、装饰性插画。
> **替代文本**：State 有三个字段，topic 和 count 被新值覆盖，log 会累加。
```

字段说明：

| 字段 | 写什么 | 为什么需要 |
| --- | --- | --- |
| 标题 | `F<课号>-<序号>｜一句话说明这张图讲什么` | 序号按在正文中出现的顺序 |
| 形式 | 静态示意图 / 流程图 / 对照图 / 截图，以及目标文件路径 | 决定用什么工具做 |
| 画什么 | 具体到画面上有哪些元素、怎么排布 | 没有这一条，画出来的一定不是你想要的 |
| 必须标注 | 缺了就看不懂的那几个标签 | 审图时逐条对 |
| 不要出现 | 容易画错、会误导的元素 | 比「画什么」更能防错 |
| 替代文本 | 一句话，读屏软件会念它 | 无障碍要求，也逼你确认图有没有信息 |

### 互动 UI

```markdown
> **互动 U01-1｜单步执行图**
> **状态**：已实现 · `apps/web/src/components/lesson-one-lab.tsx`
> **用户做什么**：点「执行下一步」，每次只走一个节点。
> **屏幕上变什么**：当前 Node 高亮；刚走过的 Edge 高亮；`count` 显示旧值→新值；`log` 追加一项。
> **通过条件**：把阈值改成 6 并跑完，`work` 恰好执行 5 次。
> **小屏**：流程横向滚动，State 面板移到下方。
```

字段说明：

| 字段 | 写什么 |
| --- | --- |
| 状态 | `已实现 · 文件路径` 或 `待开发` |
| 用户做什么 | 具体到点哪里、拖哪个、填什么 |
| 屏幕上变什么 | 每次操作之后，界面上哪些部分改变 |
| 通过条件 | 一句能判定对错的话；没有它就不是实验 |
| 小屏 | 390px 下的排布策略 |

## 三条硬规则

**不许画没跑过的结果。** 图里的数字必须能在 `lab/langgraph/` 里复现。
拿不到就写「示意」，别让读者以为那是实测。

**不许画还没实现的界面**，除非明确标成 `待开发`。截图必须来自真的能打开的页面。

**替代文本要有信息量。** 「一张流程图」等于没写。它应该是「看不到图的人读完这句话，
和看到图的人得到的信息一样多」。

## 命名与存放

```
assets/lessons/<课号>-<figure-id>.mmd     源文件
assets/lessons/<课号>-<figure-id>.svg     导出
```

`figure-id` 用短横线小写，和正文里的标题保持一致。源文件与导出一起入库，
用 `make diagrams` 渲染。视觉规范（配色、字号、线宽）见 [`02-visual-system.md`](02-visual-system.md)。

## 从需求到实现

1. 正文里写下配图/互动区块 —— 需求成立
2. 做出来，放进 `assets/lessons/` 或 `apps/web/src/components/`
3. 回到正文，把区块的**形式/状态**字段改成实际路径，图片用标准 Markdown 图片语法插进去（`!` + 方括号里的替代文本 + 圆括号里的路径）
4. 区块本身保留：它是这张图的验收标准，后人改图时要对着它看
