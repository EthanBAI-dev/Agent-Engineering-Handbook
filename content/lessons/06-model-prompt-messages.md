# 模型、Prompt 与 Messages：哪些事归模型，哪些事归你的代码

> 本课结果：给你一次真实运行，你能把里面的每个决定分给「模型」或「代码」，并说出判断依据。

## 只看一句话的话

一次 Agent 运行里的决定，大部分是你的代码定死的；模型只负责它那一小块——说什么，以及要不要提出工具调用。

> **术语说明**
>
> - **模型**：读取消息，生成下一条消息。
> - **编排器**：决定谁在什么时候被调用，以及消息流向哪里。
> - **Messages（消息列表）**：模型每次能看到的全部输入。

分不清这条边界，调试时就会一直问错问题：模型答得不对，你去改图；图接错了，你去改提示词。

## 为什么这一课要单独占一节

前五课的图里没有真实模型，所有行为都可预测。从第 07 课开始要接真实 API，行为会变得不稳定：同一个问题，两次回答可能不一样。

到那时你需要一把尺子，量一量「这次不对，到底是谁的问题」。这一课就是那把尺子。

## 消息不是一串纯文本

模型看到的不是一段拼起来的字符串，而是一个有类型的列表。

```python
SystemMessage(content="你是一个只用一句话回答的助手。")
HumanMessage(content="LangGraph 是什么？")
AIMessage(content="它是一个编排框架。")
```

> **术语说明**
>
> - **SystemMessage（系统消息）**：设定角色和规则，通常放在最前面。
> - **HumanMessage（用户消息）**：用户这一轮说的话。
> - **AIMessage（模型消息）**：模型的输出，可能是回答，也可能是工具调用请求。

实跑输出确认了每条消息都带着自己的角色：

```text
SystemMessage  role=system    你是一个只用一句话回答的助手。
HumanMessage   role=human     LangGraph 是什么？
AIMessage      role=ai        它是一个编排框架。
```

第 02 课的 `ToolMessage`（工具消息）是同一个体系里的第四种。角色不是装饰，它决定模型怎样理解这段话是谁说的。

## Prompt 不是一个字段，是你交出去的整个列表

很多教程把「Prompt」说成一个输入框。在 Agent 里，它其实是这一轮你决定交给模型的**那个消息列表**。

同一个问题，你多传一条系统消息，模型看到的输入就多一条：

```text
只传问题：模型看到 1 条输入
加上系统提示：模型看到 2 条输入
```

这也解释了第 03 课的现象：换一个 `thread_id`（会话标识），恢复出来的历史不一样，交给模型的列表就不一样，回答自然不一样。

> **术语说明｜thread_id**
> 一段会话的编号；它决定这次恢复出哪一段历史。

模型没有「记性好坏」。它只有「这次收到了什么」。

## 同一张图，换个模型，回答就变了

实验里用同一张图跑了两个不同的模型：

```text
模型 A: 它是编排多步骤流程的框架。
模型 B: 一个把 Agent 画成图来跑的库。
        消息条数 3，最后一条类型 AIMessage
```

图的结构一个字都没改：节点、边、消息条数、消息类型全都一样。变的只有那句话的内容。

反过来也成立：换一条边、加一个节点，模型再聪明也走不到你没连的地方。

> **配图 F06-1｜同一张图，换个模型只有一处会变**
> **形式**：对照图 · `assets/lessons/06-same-graph-two-models.svg`
> **画什么**：上下两栏，同一张 `START → model → END`，同一组输入消息。
> 唯一不同的是最后那条 AIMessage 的正文，用高亮框住；其余（节点、边、消息条数、消息类型）都标「相同」。
> **必须标注**：变的那一处；不变的四项。
> **不要出现**：两栏画成不同的图结构——那会毁掉本课的论点。
> **替代文本**：同一张图换一个模型，只有最终回答的措辞变了，节点、边、消息条数和类型都不变。

## 谁决定什么

这张表来自实验的最后一段输出，也是本课要你记住的全部内容：

| 决定 | 归谁 | 凭什么 |
| --- | --- | --- |
| 这次要不要调用工具 | 模型 | 它在回答里放不放 tool call |
| 有哪些工具可以调用 | 你的代码 | `bind_tools` 交出去的那份清单 |
| 工具执行的结果是什么 | 你的代码 | ToolNode 跑的是真的 Python 函数 |
| 回答用什么措辞 | 模型 | 同一张图换个模型就变了 |
| 跑完 model 之后去哪 | 你的代码 | 条件边读消息结构，不读语义 |
| 最多允许跑几轮 | 你的代码 | 模型不会自己停，见第 10 课 |

注意第五行。`tools_condition`（工具路由条件）检查的是「最后一条消息里有没有 tool call 这个结构」，不是「模型说得有没有道理」。路由从来不理解语义。

## 互动实验：把决定分类

网页实验会给你一次完整运行的事件流，每一步问同一个问题：这一步的结果，是模型定的，还是代码定的？

固定输入，固定路径，因此可以逐条判定：

1. 模型输出了 `get_weather` 的调用请求 → 模型
2. 流程从 model 走向 tools → 代码
3. 工具返回「北京：晴，24 度」 → 代码
4. 最终回答写成「北京今天晴，24 度。」 → 模型
5. 这一轮之后结束运行 → 代码

通过条件：五条全部判定正确，并且能说出第 2 条和第 5 条的依据都是条件边，而不是模型的意愿。

> **互动 U06-1｜把每个决定分给模型或代码**
> **状态**：已实现 · `apps/web/src/components/lesson-six-article.tsx`（用 `lab-kit` 的 ClassifyLab）
> **用户做什么**：给一次固定运行的五个步骤各选「模型」或「你的代码」。
> **屏幕上变什么**：选完当场判定，并给出依据；顶部计数显示答对几条。
> **通过条件**：五步全对，并能说出第 2 和第 5 步的依据都是同一条条件边。
> **小屏**：条目纵向排列，选项按钮换行。

## 本课挑战：预测哪一半会变

在运行 `06_messages.py` 之前，先写下你的预测：把脚本里模型 A 的回答改成任意一句话，重新运行后，下面哪些会变？

```text
1. 最后一条消息的内容
2. 最后一条消息的类型
3. 消息总条数
4. 图执行的节点顺序
```

正确答案是只有第 1 条会变。

如果你预测第 3 条也会变，回到第 01 课的 Reducer：消息是追加的，追加几条由节点决定，不由内容长短决定。

## 三个常见误区

### 「提示词写得好，Agent 就不会乱调工具」

提示词只能影响模型的倾向，不能构成约束。

真正的约束是代码：工具清单里没有的工具，模型再想调也调不到；条件边不允许的路线，模型再坚持也走不了。第 10 课和第 28 课会把这件事做实。

### 「模型记不住上文，是因为它记性差」

模型每次只看到你交给它的那个列表。

上一轮的消息没进列表，就等于没发生过。这不是记性问题，是第 03 课的 checkpoint（状态快照）和 `thread_id` 问题。

### 「换个更强的模型，图就不用改了」

更强的模型会让措辞和工具选择变好，但不会替你加上缺失的那条边。

如果你的图里没有 `tools → model` 回边，再强的模型也拿不到工具结果——第 02 课已经验证过这一点。

## 本课带走三句话

- 模型决定「说什么」和「要不要调用工具」
- 代码决定「有哪些工具、走哪条路、最多跑几轮」
- Prompt 不是一个字段，是你这一轮交出去的整个消息列表
