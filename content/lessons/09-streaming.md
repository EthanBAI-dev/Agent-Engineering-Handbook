# Streaming：让用户看见 Agent 正在做什么

> 本课结果：你能选对 `stream_mode`，并说出为什么直接把流里的文本全拼给用户会漏出工具的原始返回。

## 只看一句话的话

`stream` 提供几种粒度不同的事件；选错粒度，页面要么一片空白，要么把内部状态抖给用户。

> **术语说明**
>
> - **stream（流式运行）**：一边跑一边把中间事件交出来，而不是跑完一次性返回。
> - **stream_mode（流式粒度）**：决定你收到的是完整状态、节点更新，还是逐字文本。

一个会调用工具的 Agent 跑十几秒很正常。这十几秒里页面什么都没有，用户会以为它死了。

## 三种粒度，三种用途

下面每一段输出都来自实跑，问题固定是「北京天气怎么样？」，图是第 02 课那张 `model ⇄ tools`。

### `updates`：每个节点跑完，报告它改了什么

```text
[model] AIMessage → get_weather
[tools] ToolMessage → '北京：晴，24 度'
[model] AIMessage → '北京今天晴，24 度。'
共 3 个事件
```

一个节点一条，正好对应界面上「正在查天气…」这类进度提示。事件数量等于执行的节点数，可预测。

### `values`：每一步之后，给出完整 State

```text
第 0 次：messages 共 1 条
第 1 次：messages 共 2 条
第 2 次：messages 共 3 条
第 3 次：messages 共 4 条
```

注意第 0 次：图还没跑，它先把输入状态给了你。这个模式适合调试面板，**不适合直接给用户**——整份 State 里可能有系统提示和工具原始返回。

### `messages`：逐字吐出，打字机效果

这是最容易出问题的一个。照单全收的实跑结果是：

```text
照单全收：12 个文本块 → 北京：晴，24 度北京今天晴，24 度。
```

看出问题了吗？工具返回的「北京：晴，24 度」也混进去了。

## 那个坑：流里不只有模型的话

`messages` 流会吐出所有产生文本的消息，`ToolMessage`（工具消息）也在其中。它是给模型看的中间结果，不是给用户看的正文。

修法是看事件带的元数据，只保留来自 model 节点的块：

```python
for token, meta in app.stream(payload, stream_mode="messages"):
    if token.content and meta.get("langgraph_node") == "model":
        buffer += token.content
```

> **术语说明｜元数据（meta）**
> 每个流事件附带的说明，记录这个块来自哪个节点、属于哪次运行。

过滤之后的实跑结果：

```text
按节点过滤后：北京今天晴，24 度。
```

干净了。这一步不能省——省掉它，用户就会在答案前面看到一段莫名其妙的工具输出。

## 组合使用才是真实界面的样子

`stream_mode` 可以传一个列表，事件会带上自己属于哪一种：

```python
for mode, event in app.stream(payload, stream_mode=["updates", "messages"]):
    ...
```

实跑输出（截取）：

```text
▸ 进度：model 执行完毕
  · 正文块 '北京：晴，24 度'
▸ 进度：tools 执行完毕
  · 正文块 '北'
  · 正文块 '京'
  ...
▸ 进度：model 执行完毕
```

真实界面通常就是这个组合：`updates` 驱动上方的状态条，`messages`（过滤后）驱动下方逐字出现的回答。

顺带注意一个反直觉的地方：进度里 model 出现了两次。第一次它没写正文，只提出了工具调用——这正是第 02 课的结论，界面上不该把这一次显示成「正在回答」。

## 该给用户看哪一种

| 模式 | 给谁看 | 典型用途 |
| --- | --- | --- |
| `updates` | 用户 | 「正在查天气…」进度提示，一个节点一条 |
| `values` | 你自己 | 调试面板；直接给用户会把整份 State 抖出去 |
| `messages` | 用户 | 打字机效果，**必须按节点过滤** |

## 流式不改变超时，只改变体验

这一点常被误解。

流式让第一个字更早出现，用户的等待感大幅下降。但整个任务该花多久还是多久：模型该调几次调几次，工具该跑多久跑多久。

第 08 课提到的平台超时限制，流式**不能**绕开。真正需要跑很久的任务，得改成「先返回任务 id，再轮询」。

## 互动实验：给同一次运行选粒度

网页实验固定播放上面那次运行的事件流，你切换三种模式，观察同一时刻页面上出现什么：

1. `updates` → 三条进度，无正文
2. `values` → 四次状态快照，消息数 1→2→3→4
3. `messages` 不过滤 → 正文里混进「北京：晴，24 度」
4. `messages` 过滤后 → 只剩「北京今天晴，24 度。」

通过条件：指出第 3 种的问题出在哪一条消息上，并说出过滤依据是节点名而不是文本内容。

## 自己运行真实代码

完整代码位于 [`lab/langgraph/examples/09_streaming.py`](../../lab/langgraph/examples/09_streaming.py)，使用脚本化模型，**不需要 API Key**：

```powershell
uv run python examples/09_streaming.py
```

本课所有事件条数和顺序都来自这次实跑。脚本化模型逐字吐出正文，因此 `messages` 模式的块数是确定的；换成真实模型，块的切分方式由服务商决定，条数会变，但**事件的种类和顺序不变**。

这正是可以用假模型教流式的原因：粒度和过滤规则是图这一层的事，与模型无关。

## 本课挑战：数一数会有几个事件

不看答案，先预测：如果模型这次**不调用工具**，直接回答「今天晴」，那么

```text
1. updates 模式会有几个事件？
2. values 模式会打印几次？
3. messages 过滤后拼出来的是什么？
```

答案：`updates` 1 个（只有 model）；`values` 2 次（初始状态 + model 之后）；过滤后是「今天晴」。

如果你第 2 题答成 1 次，回去看 `values` 的第 0 次——图还没跑就先给了初始状态。

## 三个常见误区

### 「用了流式就不会超时」

流式改变的是用户的等待感，不是任务耗时。平台的单次请求上限照样存在。

### 「把流里的文本全拼起来就是答案」

实跑已经证明会混入工具返回。必须按节点过滤，而且判断依据是节点名，不是「看起来像不像答案」。

### 「values 模式最全，就用它」

最全也意味着最容易泄漏。系统提示、工具原始输出、内部字段都在 State 里。它是调试工具，不是响应格式——第 08 课的挑战题就是这个错误的完整版。

## 本课带走三句话

- `updates` 给进度，`messages` 给正文，`values` 只给你自己看
- `messages` 流里有 ToolMessage，必须按节点名过滤
- 流式改善体验，不改变耗时，也绕不开平台超时
