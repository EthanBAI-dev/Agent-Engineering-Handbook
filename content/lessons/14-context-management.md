# 消息太长怎么办：裁剪、过滤、总结，三种不同的取舍

> 本课结果：你能为一段过长的历史选出处理方式，并说出这个选择丢掉了什么。

## 只看一句话的话

三种方式都在丢信息，区别只在于「丢哪些」和「丢得有多明显」。

> **术语说明**
>
> - **上下文长度**：模型单次能接收的最大输入量。
> - **裁剪（trim）**：只保留最近的一部分消息。
> - **总结（summarize）**：把旧消息压成一段摘要再带上。

对话一长，每次调用都要把整段历史发给模型：费用涨、延迟涨，最后直接超出上限。

## 先认清代价

`messages` 用累加型 reducer，这是第 01 课就定下的——不累加，Agent 会只记得最后一句话。

代价是它只增不减。一段十几轮的对话，每一轮都在重发前面所有内容。第 10 课数的是调用次数，这一课数的是每次调用的大小。

## 方式一：裁剪

只保留最近的 N 条，但不能随便切：

```python
trimmed = trim_messages(
    HISTORY,
    max_tokens=4,
    token_counter=len,        # 用「条数」当计量单位，方便观察
    strategy="last",          # 留最近的
    include_system=True,      # 系统消息始终保留
    start_on="human",         # 从一条用户消息开始
)
```

13 条历史裁剪后的实跑结果：

```text
裁剪后 3 条：
  SystemMessage  你是一个客服助手。
  HumanMessage   用户第 6 句：我的订单 1006 怎么样了
  AIMessage      助手第 6 句：订单 1006 已发货
```

两个参数值得单独说：

- `include_system=True`：系统消息定义了角色和规则，切掉它模型会当场变成另一个人
- `start_on="human"`：保证截断后的历史不是从一条工具结果或半截回答开始的

> **术语说明｜token_counter（计量方式）**
> 决定「长度」怎么算。真实项目里传模型的 token 计数函数；这里传 `len`，即按消息条数算，方便观察。

裁剪的代价很直接：**旧信息直接消失，而且模型不知道自己忘了什么**。用户提到三轮前说过的地址，模型会当作没听过。

## 方式二：过滤

按规则删掉明确没用的内容：

```python
no_tool_noise = [m for m in HISTORY if not isinstance(m, AIMessage) or "已发货" not in m.content]
```

实跑结果：

```text
丢掉重复的模板回复后：13 条 → 7 条
```

过滤不花钱，也不需要模型参与，而且你完全控制删掉了什么。

限制是它只能删「规则明确」的东西：重复的模板回复、调试信息、超大的工具原始返回。它判断不了「这句话重不重要」。

一个实用做法是只保留工具返回的摘要而不是全文——一次数据库查询返回 200 行，模型真正需要的往往只有 3 行。

## 方式三：总结

把旧历史压成一段话，最近几轮保留原文：

```python
keep_recent = 4
old, recent = HISTORY[1:-keep_recent], HISTORY[-keep_recent:]
compressed = [SYSTEM, summarize(old), *recent]
```

实跑结果：

```text
13 条 → 6 条：
  SystemMessage  你是一个客服助手。
  SystemMessage  以往对话摘要：用户先后询问了 4 个订单的状态，均已发货。
  HumanMessage   用户第 5 句：我的订单 1005 怎么样了
  AIMessage      助手第 5 句：订单 1005 已发货
  HumanMessage   用户第 6 句：我的订单 1006 怎么样了
  AIMessage      助手第 6 句：订单 1006 已发货
```

代价有两条，都不小：

1. 摘要要多花一次模型调用——这次调用也要算进第 10 课的预算
2. 摘要本身可能丢掉关键细节，而且丢得很隐蔽

第 2 条尤其要小心。用户三轮前说过「我的收货地址改成公司了」，摘要写成「用户咨询了订单状态」，这条信息就永久消失了，而且看起来一切正常。

## 三种方式怎么选

| 方式 | 好处 | 代价 |
| --- | --- | --- |
| 裁剪 | 最快，零成本 | 旧信息直接消失，模型不知道自己忘了什么 |
| 过滤 | 零成本，可精确控制 | 只能删规则明确的内容，判断不了重要性 |
| 总结 | 旧信息以压缩形式留下 | 多一次模型调用，摘要可能丢关键细节 |

常见组合是三种一起用：

```text
系统消息永远保留
  + 最近 N 轮原文
  + 更早的内容压成一段摘要
  + 工具返回只留摘要，不留全文
```

> **配图 F14-1｜三种方式各丢掉什么**
> **形式**：三列对照图 · `assets/lessons/14-three-strategies.svg`
> **画什么**：同一段 13 条历史，三列处理结果。裁剪列把旧消息整段划掉；过滤列挑掉几条模板回复；
> 总结列把旧消息压成一张摘要卡。每列底部标代价。
> **必须标注**：三列都要标出「丢了什么」；总结列额外标「多一次模型调用」。
> **不要出现**：暗示存在不丢信息的方案。
> **替代文本**：裁剪直接丢弃旧消息，过滤按规则删除，总结压缩成摘要但要多一次模型调用，三者都在丢信息。

## 这不是长期记忆

本课处理的是「这一次调用发多少内容」。它和第 03 课的会话记忆、第 30 课的长期记忆是三件事：

```text
第 03 课  会话记忆：这段对话的历史存在哪里
第 14 课  上下文管理：这一次调用带上其中的哪些
第 30 课  长期记忆：跨会话该记住这个用户的什么
```

裁剪掉的消息仍然在 checkpoint 里躺着，只是这次没发给模型。需要时还能取回来——前提是你别把它从 State 里真的删掉。

**建议：裁剪发生在「交给模型之前」，而不是「写进 State 之前」。**保留完整历史，每次调用时按需裁剪，这样第 18 课的 Time Travel 才有东西可回放。

## 互动实验：在预算内保住关键信息

网页实验给一段 13 条的历史，其中第 3 条藏着一个关键事实（用户改过收货地址）。你的预算是 6 条。

```text
只裁剪        →  关键事实丢失
裁剪 + 摘要   →  取决于摘要有没有抓住它
过滤 + 裁剪   →  关键事实保住，但删掉了模板回复
```

通过条件：在 6 条预算内让关键事实仍然可见，并说出你的方案丢掉了什么。

**没有不丢信息的方案**，这正是本课要传达的判断。

## 本课挑战：这个裁剪错在哪

```python
def call_model(state):
    state["messages"] = state["messages"][-6:]   # 直接改 State
    return {"messages": [model.invoke(state["messages"])]}
```

两个问题：

1. 它原地修改了 State——第 13 课刚说过，这会破坏 checkpoint 里的历史
2. 它把裁剪做在了「写进 State」这一层，被切掉的消息永久消失

正确做法是只在交给模型时裁剪，State 里保留完整历史：

```python
def call_model(state):
    visible = trim_messages(state["messages"], ...)
    return {"messages": [model.invoke(visible)]}
```

## 三个常见误区

### 「上下文窗口够大就不用管」

窗口大只是把问题推后。每次调用的费用和延迟都跟输入长度走，一段长对话的成本会一路涨上去。

### 「让模型自己判断该记住什么」

那是又一次模型调用，同样会出错，而且出错时你看不出来。先用规则能解决的部分，剩下的再交给模型。

### 「摘要之后就可以删掉原文了」

删了就回不去了。摘要放在发给模型的那一侧，原文留在 State 里——两者不冲突。

## 本课带走三句话

- 三种方式都在丢信息，区别在丢哪些、丢得明不明显
- 裁剪要保住系统消息，并且从一条完整的用户消息开始
- 裁剪发生在交给模型之前，不是写进 State 之前
