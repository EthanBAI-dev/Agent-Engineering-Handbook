# 建立 /api/agent：让网页真正调用得到 Python LangGraph

> 本课结果：你能画出一次请求从浏览器到图、再回到浏览器的完整路径，并说清 Python 代码到底跑在哪里。

## 只看一句话的话

浏览器发一个普通的 HTTP 请求给你自己的接口，接口在服务端跑图，再把结果作为普通 JSON 返回。

> **术语说明**
>
> - **HTTP 请求**：浏览器向某个地址要数据的标准方式。
> - **接口（API endpoint）**：服务端上一个固定地址，接收请求并返回结果。
> - **JSON**：一种通用的数据格式，前后端都能读。

这中间没有魔法。难点不在「怎样调用图」，在**Python 跑在哪里**。

## 先承认一个现实

本课程的图是 Python 写的，网站是 Next.js 写的。它们不是同一个运行时。

把它们接起来只有两种现实做法：

```text
方案 A：同一个项目，两种运行时
  网页（Node.js）  →  /api/agent（Python 函数）  →  图

方案 B：两个服务
  网页（Node.js）  →  /api/agent（Node.js 转发）  →  独立 Python 服务  →  图
```

方案 A 部署简单，但受平台对 Python 函数的支持和启动时间限制。方案 B 多一次网络跳转，但 Python 服务可以自己选环境、自己扩容，长期更省心。

> **术语说明｜运行时**
> 真正执行代码的环境。Node.js 跑不了 Python，反过来也一样。

课程后续按方案 B 推进：它更接近你以后真的要维护的形态，也避免把课程绑死在某个平台的限制上。

## 接口契约：先定，再写

在写任何代码之前，先把这个接口的输入输出定下来。契约定不清楚，前后端会各写各的。

**请求**：

```json
{
  "thread_id": "a",
  "message": "北京天气怎么样？"
}
```

**响应**：

```json
{
  "thread_id": "a",
  "reply": "北京今天晴，24 度。",
  "steps": ["model", "tools", "model"],
  "model_calls": 2
}
```

三个字段值得解释：

- `thread_id` 原样回传，前端才能确认「这是刚才那段会话的回复」，而不是另一个请求的
- `steps` 让前端可以显示走过哪些节点，对应第 09 课的进度提示
- `model_calls` 让前端知道这次消耗了多少，对应第 10 课的限额

> **术语说明｜契约**
> 双方约好的输入输出格式。它先于实现存在，改动它要两边一起改。

## 服务端要做的四件事

```python
# 伪代码：说明顺序，不是可直接运行的完整服务
def handle(request):
    body = parse_json(request)                  # 1. 取出输入
    if not valid(body):                          # 2. 校验
        return error(400, "message 不能为空")
    config = {"configurable": {"thread_id": body["thread_id"]}}
    result = app.invoke(                         # 3. 跑图
        {"messages": [("user", body["message"])]}, config
    )
    return json({                                # 4. 只返回该返回的
        "thread_id": body["thread_id"],
        "reply": result["messages"][-1].content,
    })
```

第 4 步最容易做错。不要把整个 State 直接返回给前端：里面可能包含系统提示、工具的原始返回、内部字段。第 03 课已经说过，`thread_id` 不是身份验证——接口返回什么，必须是你主动挑选的，不是顺手全给。

> **术语说明｜校验**
> 在使用输入之前检查它是否合法。外部输入永远不可信，这是第 28 课的开头。

## 一次请求的完整路径

```text
浏览器 fetch("/api/agent", {...})
   │
   ├─ 网页服务端：校验输入，取出 thread_id
   │     │
   │     └─ Python 服务：app.invoke(...)
   │            │
   │            ├─ checkpointer 恢复这个 thread 的历史
   │            ├─ model 节点 → 真实模型 API
   │            ├─ tools 节点 → 真实函数
   │            └─ 保存新的 checkpoint
   │
   └─ 浏览器收到 JSON，渲染回复
```

前四课学的东西，在这张图里全部出现了：State、条件边、checkpointer、thread_id。接口没有引入新的 Agent 概念，它只是把图搬到了网络另一头。

## 三个必须提前想清楚的问题

**超时。** 无服务器平台通常对单次请求有时间上限。一个会调用多轮工具的 Agent 很容易撞上。解决方向是第 09 课的流式返回，或者把长任务改成「先返回任务 id，再轮询」。

**冷启动。** 一段时间没人访问，下一次请求要先启动进程。第一个用户会等得更久。

**进程不连续。** 这一点直接影响第 03 课的结论：`InMemorySaver`（内存检查点保存器）把快照放在进程内存里，而线上两次请求不保证落在同一个进程。所以上线的那一刻，会话记忆必须换成外部存储——这是第 15 课的内容。

> **术语说明｜冷启动**
> 服务从完全停止的状态被唤醒并准备好处理请求的过程。

## 互动实验：把请求路径排对

网页实验给出七张打乱的卡片：

```text
浏览器 fetch    ·    校验输入    ·    恢复 checkpoint
model 节点     ·    tools 节点  ·    保存 checkpoint    ·    返回 JSON
```

你把它们排成一次完整请求的顺序，并标出哪几步发生在服务端。

通过条件：顺序正确，并且「校验输入」之后的所有步骤都被标为服务端。这也是本课唯一必须记住的安全事实——校验和密钥都在服务端那一侧。

## 自己运行真实代码

**这一课没有可实跑的脚本，这是有意为之。**

本仓库当前处于第一阶段：不接模型 API、不接账号和数据库。接口一旦上线，就必须同时具备第 10 课的限额和第 28 课的输入校验，否则等于把你的模型额度开放给互联网。

因此本课的代码是**设计稿**，不是已验证实现。课程不声称本仓库已经部署过任何线上地址。

你现在可以做的验证是本地的：把上面的契约写成一份 JSON 示例文件，用它跟前端先对齐字段名。契约对齐的成本，比接口写完再改低得多。

## 本课挑战：找出这个响应的三个问题

```json
{
  "state": {
    "messages": [
      {"role": "system", "content": "你是一个内部客服，可以查询订单表 orders"},
      {"role": "user", "content": "我的订单到哪了"},
      {"role": "tool", "content": "SELECT * FROM orders WHERE id=1024 → 已发货"},
      {"role": "assistant", "content": "您的订单已发货。"}
    ]
  },
  "api_key_used": "sk-ant-abc123",
  "thread_id": "a"
}
```

三个问题：

1. 返回了整个 State，把系统提示和内部表名暴露给了前端
2. 返回了工具的原始输出，里面有 SQL 和内部数据结构
3. 返回了 API Key——这一条足以让密钥彻底作废

正确的响应只需要 `thread_id` 和 `reply`，加上你确实要显示的进度字段。

## 三个常见误区

### 「前端直接调用模型服务商的接口更简单」

简单，也等于把密钥发给每个访问者。第 07 课已经算过这笔账。

### 「接口能跑通就算完成」

能跑通只证明顺路径没问题。上线还需要：输入校验、调用上限、超时处理、错误响应格式。缺一样，第一个异常请求就会暴露它。

### 「会话记忆已经在第 03 课解决了」

第 03 课解决的是「同一个进程里」。线上进程不连续，`InMemorySaver` 会让用户随机失忆。这个坑留到第 15 课换成外部 checkpointer 才算填上。

## 本课带走三句话

- 浏览器只发问题、收答案，密钥和校验都在服务端
- 接口契约先定再写，响应只返回你主动挑选的字段
- 上线会打破「同一个进程」的假设，内存里的会话记忆撑不住
