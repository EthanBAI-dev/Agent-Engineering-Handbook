# 调用限额与成本：模型不会自己停，得你来停

> 本课结果：你能给一张图加上每次请求的调用上限，并让超限的请求得到一句像样的回复，而不是抛异常或静默返回半截结果。

## 只看一句话的话

「让提示词告诉它别循环太久」不是控制；控制是代码里一条数得清的硬上限。

> **术语说明**
>
> - **限额（quota）**：单次请求或单个用户允许消耗的资源上限。
> - **硬上限**：由代码强制执行、模型无法绕过的数值。

上线第一个 Agent 之后，最先出事的通常不是回答质量，是账单和响应时间。

## 为什么工具循环会停不下来

回到第 02 课的闭环：`model → tools → model`。这个循环的出口只有一个——模型不再提出工具调用。

也就是说，**是否结束由模型决定**。这在教学示例里没问题，在线上就成了敞口：

```text
模型：再搜一次
工具：这里还有更多资料
模型：那再搜一次
工具：这里还有更多资料
...
```

模型没有出错，它每一步都很合理。合理的一步 × 30 次，就是一张账单和一个超时。

## 加一个数得清的计数器

给 State 多加一个字段，model 节点每跑一次就加一：

```python
class BudgetState(TypedDict):
    messages: Annotated[list, add_messages]
    model_calls: int

def call_model(state: BudgetState) -> dict:
    return {
        "messages": [model.invoke(state["messages"])],
        "model_calls": state["model_calls"] + 1,
    }
```

> **术语说明｜计数字段**
> 普通的覆盖型字段。它和 `messages` 不一样：`messages` 用 Reducer 累加，计数用新值覆盖旧值——这正是第 01 课那条区别。

然后把判断放进条件边：

```python
def route(state: BudgetState) -> str:
    if state["model_calls"] >= MAX_MODEL_CALLS:
        return "stop_note"
    return "tools" if state["messages"][-1].tool_calls else END
```

## 顺序不能反

上面这段代码里，**先查预算，再看 `tool_calls`**。

反过来写：

```python
# 错误示范
if state["messages"][-1].tool_calls:
    return "tools"
if state["model_calls"] >= MAX_MODEL_CALLS:
    return "stop_note"
```

只要模型还想调用工具，第一条就命中了，预算检查永远轮不到。上限形同虚设。

这类 bug 不会报错，只会在账单上出现。

## 超限之后要说人话

到了上限直接抛异常，用户看到的是一个 500 错误。正确做法是走一个专门的节点，给一句能理解的回复：

```python
def stop_note(state: BudgetState) -> dict:
    return {
        "messages": [
            AIMessage(content=f"已达本次请求上限（{MAX_MODEL_CALLS} 次模型调用），先返回目前的进展。")
        ]
    }
```

这条消息同样进 `messages`，所以它会作为最后一条被返回给前端，前端不需要为「被截断」写特殊分支。

## 两条路径的实跑结果

上限设为 3 次。

**正常请求**：模型调一次工具，第二轮给出答案。

```text
模型调用 2 次，上限 3 次
消息共 4 条
最后一条：查到了，资料在官网。
```

没碰到上限，限额完全不影响正常使用——这是一个好限额的标志。

**失控请求**：模型每一轮都想再搜一次，永远不给最终回答。

```text
模型调用 3 次，上限 3 次
消息共 7 条
最后一条：已达本次请求上限（3 次模型调用），先返回目前的进展。
```

停在第 3 次，没有第 4 次，用户拿到一句说得通的话。

> **配图 F10-1｜预算判断必须在第一位**
> **形式**：对照图 · `assets/lessons/10-route-order.svg`
> **画什么**：左右两栏画同一个条件边的两种写法。左栏先查预算再看 `tool_calls`，标「上限生效」；
> 右栏顺序反过来，第二个判断整块灰掉并标「死代码」。
> **必须标注**：右栏那句「只要模型还想调用工具，预算检查永远轮不到」。
> **不要出现**：把右栏画成会报错——它不报错，只会出现在账单上，这才是它危险的地方。
> **替代文本**：先查预算再看工具调用，上限才生效；顺序反过来，预算检查就成了永远执行不到的死代码。

## 这一层之外还有两层

本课做的是**单次请求**的上限。真正上线还差两层：

| 层级 | 挡住什么 | 本课是否覆盖 |
| --- | --- | --- |
| 单次请求的调用上限 | 一个请求里的死循环 | 是 |
| 单个用户的用量配额 | 一个人反复发请求 | 否，需要账号，见第 29 课 |
| 全站的总预算与告警 | 所有人加起来烧超 | 否，需要计费侧的监控 |

只做第一层就上线，等于「每个请求都很克制，但请求数量不受限」。在没有第 29 课的账号体系之前，接口不要公开暴露。

> **术语说明｜配额**
> 按用户或按时间窗口分配的用量额度，例如「每人每天 20 次」。

## 除了次数，还该数什么

调用次数是最容易数、也最该先加的一个。此外还有两个常见维度：

- **token 用量**：更贴近真实成本，但要等模型返回后才知道，只能事后累计、下次拒绝
- **墙上时间**：给整个请求设一个秒数上限，防的是「每一步都不慢，但步数太多」

先做次数上限。它是唯一一个在调用发生**之前**就能拦住的。

## 互动实验：调上限，看两条路径

网页实验固定使用上面那个停不下来的模型，你只能改一个数字——上限。

```text
上限 = 1  →  第 1 次调用后立刻截断，消息 3 条
上限 = 3  →  截断在第 3 次，消息 7 条
上限 = 8  →  截断在第 8 次，消息 17 条
```

每次多允许一轮，就多出一次 model 调用和一条工具结果，共 2 条消息。

通过条件：预测上限为 5 时的消息条数（答案是 11 条），并说出为什么是 2 的倍数加 1——一条用户消息，加上每轮的模型消息和工具消息。

> **互动 U10-1｜调上限，看两条路径**
> **状态**：已实现 · `apps/web/src/components/lesson-ten-article.tsx`（ScenarioLab）
> **用户做什么**：拖上限滑杆，切换模型行为（两轮收工／停不下来），再把条件边的判断顺序调反。
> **屏幕上变什么**：调用次数、消息条数与最后一条消息实时更新；顺序调反时消息「一直增长」，并说明预算检查成了死代码。
> **通过条件**：预算判断在第一位，且失控请求被截断并给出说明。
> **小屏**：滑杆与两组分段控件纵向排列。

## 本课挑战：这个限额为什么没生效

```python
def route(state):
    last = state["messages"][-1]
    if last.tool_calls:
        return "tools"
    if state["model_calls"] >= MAX_MODEL_CALLS:
        return "stop_note"
    return END
```

问题：只要模型持续提出工具调用，第一个 `if` 永远先命中，预算检查是死代码。

修法是把预算判断提到最前面。判断标准很简单：**上限必须是第一道，不是最后一道**。

## 三个常见误区

### 「在提示词里写『最多查三次』就够了」

提示词是建议，不是约束。模型可能遵守，也可能在长对话里忘掉。能强制执行的只有代码。

### 「加上限会影响正常用户」

实跑的第一条路径已经证明不会：正常请求用了 2 次，上限 3 次，完全没被触碰。

上限该设在「异常」和「正常」之间，而不是卡着正常值设。设不准就先记录真实分布，再定数值。

### 「超限抛个异常就行」

异常对用户是一个 500 页面，对前端是一个需要特殊处理的分支。走 `stop_note` 节点则让截断成为一条普通消息，前后端都不需要额外分支。

## 本课带走三句话

- 结束循环的权力不能留给模型，要留给一个计数器
- 预算判断必须放在条件边的第一位，否则是死代码
- 超限走一个专门节点，给用户一句说得通的话
