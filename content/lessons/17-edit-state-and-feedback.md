# 人工修改 State：审批不该只有同意和拒绝两个按钮

> 本课结果：你能在审批时直接改掉参数再继续，并说出「改当前 State」和「退回重新生成」的区别。

## 只看一句话的话

人看到提案后最常见的反应是「方向对，参数不对」；只给两个按钮，人就只能拒绝。

> **术语说明**
>
> - **update_state**：从外部修改某个 thread 当前的 State。
> - **as_node**：告诉 LangGraph「这次修改就当是那个节点写的」。

## 两个按钮不够用

Agent 提出：清理 `/` 下超过 7 天的文件。

范围太大了。但问题不在方向——清理旧文件是对的，只是不该从根目录开始。

只能拒绝的话，实跑结果是这样：

```text
Agent 提案：清理 / 下超过 7 天的文件
人：范围是整个根目录，太危险了 → 拒绝
结果：已取消
```

然后呢？Agent 什么也没学到，你要重新描述一遍需求，它可能再提一个类似的方案。人明明已经知道正确答案了，却没有地方把它填进去。

## 改法一：直接改当前 State

```python
app.update_state(cfg, {"target": "/tmp", "days": 30}, as_node="propose")
```

实跑结果：

```text
改完之后 State：target=/tmp days=30
下一个要跑的节点：('review',)
结果：已执行：清理 / 下超过 7 天的文件
```

参数改对了，图从原地继续。但看最后一行——**执行的还是旧提案**。

## 那句「结果」为什么是旧的

因为 `plan` 这个字段是 `propose` 节点上一次算出来的。你改的是 `target` 和 `days`，没有改 `plan`，也没有让 `propose` 重新跑一遍。

这不是 bug，是 State 的本来行为：**改一个字段不会自动重算依赖它的其他字段**。

第 12 课说 State 是一份合同，这里就是合同的代价——字段之间的推导关系不在合同里，它藏在节点代码中。

所以改当前 State 只适合一种情况：**你要改的字段，后面没有别的字段依赖它**。

## 改法二：退回到更早的一步，重新生成

如果改动会影响后续推理，就回到那一步之前再改：

```python
history = list(app.get_state_history(cfg))
before_propose = [h for h in history if h.next == ("propose",)][0]
forked = app.update_state(before_propose.config, {"target": "/tmp", "days": 30})
out = app.invoke(None, forked)
```

实跑结果：

```text
重新生成的提案：清理 /tmp 下超过 30 天的文件
结果：已执行：清理 /tmp 下超过 30 天的文件
```

这一次 `propose` 用新参数重新跑了一遍，提案和参数对上了。

代价是多花一次节点执行——如果那个节点会调用模型，就是多一次模型调用，要算进第 10 课的预算。

> **注意**：从一个旧快照分叉跑过之后，恢复要用**线程级 config**（不带 `checkpoint_id` 的那个），因为这条 thread 的最新状态已经往前走了。写实验时这里踩过一次，恢复用了旧的 forked config，结果什么都没执行。

## 两种改法怎么选

| 情况 | 选哪种 | 理由 |
| --- | --- | --- |
| 人已经想清楚最终参数 | 改当前 State | 省一次模型调用，最快 |
| 改动会影响后续推理 | 退回重新生成 | 让 Agent 基于新参数重新想一遍 |
| 只是修个错别字 | 改当前 State | 没有下游依赖 |
| 改的是任务目标 | 退回重新生成 | 目标变了，整个计划都要重来 |

判断标准只有一条：**这个字段，后面还有别的东西是根据它算出来的吗？**

## 共同前提

两种改法都依赖 checkpointer。

没有它，「原地」和「更早的一步」都不存在——第 04 课那句「human-in-the-loop 必须配 checkpointer」，在这一课变成了两条能力的地基。

## 让人能改，界面就要给得出

技术上能改，不等于人改得了。审批界面至少要提供：

- 提案的**具体参数**，而不是一句概括（「清理旧文件」看不出范围是 `/` 还是 `/tmp`）
- 可以直接编辑的输入框，而不只是同意／拒绝
- 说明哪些字段改了之后会重新推理，哪些不会

最后一条尤其重要。人改完 `days` 却发现执行的还是旧计划，会认为这个系统在骗他——而这只是没有告诉他 `plan` 不会自动重算。

## 互动实验：三种反应

网页实验固定给出那个「清理 `/` 下 7 天文件」的提案，你选择怎么处理：

```text
拒绝              →  流程结束，什么都没发生
改参数后继续      →  参数变了，但计划文本还是旧的
退回重新生成      →  参数和计划都对上了
```

面板同时显示 `target`、`days`、`plan` 三个字段，让「改了什么」和「哪些跟着变了」一眼可见。

通过条件：说出第 2 种为什么 `plan` 没变，并指出什么时候第 2 种反而更合适。

完整代码位于 [`lab/langgraph/examples/17_edit_state.py`](../../lab/langgraph/examples/17_edit_state.py)，**不需要 API Key**：

```powershell

```

三段实跑输出都来自这个脚本。建议自己加一个字段试试：让 `propose` 同时算出一个 `risk_level`，然后只改 `days`，观察 `risk_level` 会不会跟着变。

## 本课挑战：这样改为什么不安全

```python
# 让人直接编辑整个 State
app.update_state(cfg, request.json["state"])
```

问题：把外部输入原样写进 State。

审批界面是网页，`request.json` 是用户可以任意构造的。这段代码允许审批者改**任何**字段——包括 `level`（第 16 课的风险级别）、`op_id`（第 19 课的幂等键），甚至是本该由服务端决定的用户身份。

正确做法是只允许改一份白名单里的字段：

```python
ALLOWED = {"target", "days"}
patch = {k: v for k, v in request.json["state"].items() if k in ALLOWED}
app.update_state(cfg, patch)
```

这和第 11 课的路由白名单是同一条原则：**外部来的值进入系统之前，先过一道你自己的清单。**

## 三个常见误区

### 「改了 State，相关字段会自动更新」

不会。State 是一组字段，不是一张依赖图。要重算就得让对应节点重新跑。

### 「update_state 可以随便改，反正有审批的人把关」

审批的人只看得到界面上显示的内容。接口层面能改什么，必须由服务端白名单决定。

### 「退回重新生成更准，那就一律用它」

它要多花一次节点执行。如果那个节点调用模型，成本和延迟都会上去。只改错别字的时候没必要重来。

## 本课带走三句话

- 审批要有第三个选项：改一下再继续
- 改字段不会重算依赖它的字段，要重算就退回那一步之前
- 允许改哪些字段，由服务端白名单决定，不由界面决定
