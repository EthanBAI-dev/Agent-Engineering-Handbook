# Multi-Agent：先证明你真的需要第二个 Agent

> 本课结果：你能算出一次交接丢了多少信息，并说出什么情况下这个代价值得付。

## 只看一句话的话

多一个 Agent 就多一层交接，而交接一定会丢东西——问题永远是「为了换来什么」。

> **术语说明**
>
> - **交接（handoff）**：一个 Agent 把工作转给另一个时传过去的内容。
> - **交接损耗**：交接内容小于完整现场时，必然丢失的那部分信息。

「多 Agent 协作」听起来比「一张图」高级，所以它常被当成默认选择。这一课不教怎么搭，教怎么判断该不该搭。

## 先看一张图的基线

```python
def collect(state):
    return {"notes": [f"{k}={v}" for k, v in FACTS.items()], ...}

def draft(state):
    # 它能看到 collect 留下的全部内容，一条都没丢
    return {"output": "；".join(state["notes"]), ...}
```

实跑结果：

```text
模型调用 2 次
产出：客户=张三；金额=1200 元；日期=3 月 5 日
信息完整度：3/3 条事实都在
```

两个步骤共享同一份 State，所以第二步能看到第一步的**全部现场**，不是摘要。

## 再看两个 Agent

```python
def agent_a(state):
    """收集 Agent。它把结果压成一段话交给下一个 Agent。"""
    summary = model.invoke("总结")
    return {"handoff": summary.content, ...}

def agent_b(state):
    """撰写 Agent。它只看得到 handoff，看不到 A 的工作现场。"""
    ...
```

实跑结果：

```text
模型调用 2 次
交接内容：客户张三，金额 1200 元。
信息完整度：2/3 条事实活着通过了交接
丢掉的：['日期']
```

日期没了。A 知道日期，但没写进交接文本，B 就再也看不到了。

## 这不是没写好，是结构决定的

有人会说：让 A 写得更全就行了。

那就试试推到极限——如果交接内容是**完整的 State**，会怎样？

那它和一张图就没有区别了，只是多了一次调用和一次序列化。你付出了成本，没换来任何隔离。

反过来，如果交接内容是**摘要**，那就一定会丢东西——摘要的定义就是丢东西。

```text
交接 = 完整 State  →  等于一张图，白付成本
交接 = 摘要        →  一定丢信息
```

**没有第三种可能。**所以问题永远是：为了换来什么，值得丢这些？

## 什么时候值得

| 情况 | 选哪个 | 原因 |
| --- | --- | --- |
| 步骤多但目标单一 | 一张图 | 共享 State 没有损耗，调试也简单 |
| 需要不同的工具权限 | 多 Agent | 把危险工具关在一个 Agent 里，其他 Agent 拿不到 |
| 需要不同的模型或成本档位 | 多 Agent | 简单活给便宜模型，难的给贵的 |
| 由不同团队维护和发布 | 多 Agent | 边界即接口，能各自升级 |
| 只是想让流程看起来清晰 | 一张图 | 用子图就够了，第 23 课 |
| 想让 Agent 互相检查 | 看情况 | 先试同一张图里加一个检查节点，通常够用 |

第二行是最硬的理由，也和第 16、28 课直接相关：**如果一个 Agent 根本拿不到删除工具，它就不可能误删**。这种隔离是结构性的，比任何提示词都可靠。

第三行是成本理由。一个便宜模型做分类、一个贵模型做撰写，可以省下不少钱——前提是分类这一步不需要看到完整现场。

## 一个判断标准

**能用一句话说清「这两个 Agent 各自不许知道什么」吗？**

- 说得清 → 这条边界是真的，多 Agent 有意义
- 说不清 → 你要的其实是子图，不是第二个 Agent

「A 负责收集，B 负责撰写」不是边界，那只是分工——分工用子图或者两个节点就能表达，不需要切断信息。

「B 不许拿到数据库写权限」才是边界。

## 多 Agent 的三笔额外成本

**调试变难。**出了问题要先判断是 A 给错了，还是 B 理解错了。第 18 课的时间旅行还能用，但你要在两条时间线之间对照。

**成本上升。**交接本身往往要一次模型调用来生成摘要。两个 Agent 常常意味着三次调用而不是两次。

**失败面变大。**每个交接点都是一个可能出错的地方，而且这类错误是「信息悄悄少了一块」，不会报错。

## 互动实验：数一数丢了什么

网页实验给你五条事实和一个两 Agent 流程，你控制交接内容的长度：

```text
交接 = 完整现场      →  5/5 保留，但和一张图没区别
交接 = 一句话摘要    →  2/5 保留
交接 = 三句话摘要    →  4/5 保留，成本更高
```

通过条件：说出你会选哪一档，以及这个选择需要什么理由来支撑。

## 本课挑战：这个多 Agent 有意义吗

```text
Agent 1：读取用户的问题，判断是技术问题还是账务问题
Agent 2：如果是技术问题，查文档并回答
Agent 3：如果是账务问题，查订单并回答
```

答案：大概率没有意义，这是第 11 课的 Router 加两个分支。

三个「Agent」共享同一个目标、同一份用户问题，也没有任何一个需要对另一个隐藏信息。把它写成一张图，路由节点加两个分支节点，代码更短、没有交接损耗、调试也简单。

**除非**——Agent 3 需要访问订单数据库，而你不希望 Agent 2 有这个权限。那这条边界就是真的，多 Agent 成立。

判断依据不是流程图长什么样，是**有没有一条必须切断的信息边界**。

## 三个常见误区

### 「多 Agent 更接近真实团队协作」

真实团队协作也有交接损耗，只是人会主动追问。Agent 不会——它拿到什么就用什么，缺了什么它不知道。

### 「让 Agent 互相审查，质量会更高」

同一张图里加一个检查节点通常就够了，而且检查节点能看到完整现场，判断更准。切成两个 Agent 反而让检查方看得更少。

### 「先按多 Agent 设计，以后好扩展」

多出来的交接层从第一天就开始收费，而扩展需求可能永远不来。需要的时候再拆——第 23 课的子图已经让拆分很便宜了。

## 本课带走三句话

- 交接不是完整 State 就一定丢信息，是完整 State 就等于一张图
- 真正的理由是权限隔离、成本分档、团队边界，不是「看起来清晰」
- 说不清两个 Agent 各自不许知道什么，你要的就是子图
