# 审批策略：什么动作必须问人，什么动作根本不该给

> 本课结果：你能给一张工具表配上自动、审批、禁止三个级别，并说出未登记的工具为什么按最严格处理。

## 只看一句话的话

能自动跑的自动跑，危险的才问，绝不该做的直接不给——三档，不是两档。

> **术语说明**
>
> - **风险分级**：按后果严重程度决定一个动作要不要人来确认。
> - **默认拒绝**：不在允许清单里的动作一律按最严格处理。

第 04 课让图在删除前停下来等人点头。这一课要解决的是：十几个工具，该在哪几个上停。

## 审批太多，等于没有审批

如果每个工具都要确认，人会在第五次弹窗之后开始闭眼点「同意」。

这不是用户素质问题，是设计问题。**审批是一种稀缺资源**：它值钱，是因为它少。一旦变成流水线上的例行动作，它就只剩下「出事后可以说用户同意过」的免责功能，不再提供任何保护。

所以设计审批策略的第一步，不是列出哪些要问，而是**尽可能多地划进「不用问」**。

## 三个级别

```python
POLICY: dict[str, Risk] = {
    "read_file": "auto",      # 只读，可逆，范围可控
    "list_dir": "auto",
    "move_file": "approve",   # 有副作用，但可撤销
    "delete_file": "approve", # 有副作用，难撤销
    "send_email": "approve",  # 一旦发出无法收回
    "drop_table": "forbid",   # 不该由 Agent 做的事
}
```

分级的依据是**后果**，不是「感觉危不危险」：

| 级别 | 判断标准 | 典型动作 |
| --- | --- | --- |
| `auto` | 没有副作用，或副作用完全可逆 | 读文件、查数据库、算数 |
| `approve` | 有外部可见的副作用，撤销代价高 | 删除、发邮件、扣款、改配置 |
| `forbid` | 后果不可接受，或不该由 Agent 决定 | 删库、改权限、转账 |

`forbid` 这一档最容易被忽略。很多人把所有危险动作都放进 `approve`，觉得「反正有人把关」。但有些事的正确答案是**根本不提供这个工具**——人在疲劳时点错一次的代价，可能是不可逆的。

## 这张表必须是代码

风险表写在代码里，不写在提示词里。

第 06 课已经说过这条边界：提示词是建议，模型可能遵守也可能忘掉；代码是约束，模型绕不过去。一份写在系统提示里的「危险操作请先询问用户」，在长对话里失效是常态。

## 默认拒绝

`classify` 节点只有一行，但那一行是本课最重要的一行：

```python
return {"decision": POLICY.get(state["tool"], "forbid")}
```

`POLICY.get(tool, "forbid")` —— 查不到的工具，按 `forbid` 处理。

实跑验证了这个行为：

```text
[transfer_money] 级别=forbid  没有打断
              → 策略禁止：transfer_money 不在允许清单内，不会询问，也不会执行
```

如果这里的默认值写成 `"auto"` 或 `"approve"`，那么每当有人新增一个工具却忘了登记，它就会自动获得权限。**新增工具时忘记登记是必然会发生的事**，所以默认值必须站在安全那一边。

## 三个级别的实跑结果

```text
[read_file  ] 级别=auto    没有打断
              → 直接执行 read_file(notes.md)

[delete_file] 级别=approve  停下来问：允许执行 delete_file(/tmp/cache) 吗？
              人回答 'yes'
              → 经批准后执行 delete_file(/tmp/cache)

[delete_file] 级别=approve  停下来问：允许执行 delete_file(/etc/passwd) 吗？
              人回答 'no'
              → 用户拒绝，未执行 delete_file

[drop_table ] 级别=forbid  没有打断
              → 策略禁止：drop_table 不在允许清单内，不会询问，也不会执行
```

注意第四条：`forbid` **不询问**。

这一点值得强调。如果禁止级操作也弹窗，就等于告诉用户「这件事点一下是可以做的」。真正不该做的事，不要给人犯错的机会。

## 审批要问得清楚

打断时交出去的内容，决定了人能不能做出正确判断：

```python
answer = interrupt({
    "question": f"允许执行 {state['tool']}({state['args']}) 吗？",
    "risk": "有副作用，可能无法撤销",
})
```

一个合格的审批提示至少要说清三件事：**做什么、对谁做、做了之后能不能撤销**。

「Agent 想执行一个操作，是否允许？」这种提示等于没问——人没有任何判断依据，只能凭心情点。

## 本课挑战：这份策略表哪里不安全

```python
POLICY = {
    "read_file": "auto",
    "delete_file": "approve",
    "send_email": "auto",          # 群发通知用，很频繁
}
default = "approve"
```

两个问题：

1. `send_email` 定成 `auto`，理由是「很频繁」。但频繁不等于安全——邮件发出去收不回来，这是典型的 `approve` 级动作。**用频率决定级别，是最常见的错误。**
2. 默认值是 `approve` 而不是 `forbid`。新增工具忘了登记时，它会自动获得「问一下就能执行」的权限，而人往往会同意一个自己不了解的操作。

## 三个常见误区

### 「都交给人审批最安全」

审批太多会导致闭眼同意，实际保护为零，还额外拖慢了每一次运行。安全来自「危险动作少而明确」，不是「弹窗多」。

### 「在提示词里写清楚就行」

第 06 课验证过：提示词影响倾向，代码构成约束。风险表放代码里。

### 「forbid 的工具也弹个窗，让用户自己决定」

给用户一个不该存在的按钮，就是在等它被按下。真正不该做的事，从工具清单里拿掉。

## 本课带走三句话

- 三档而不是两档：`forbid` 那一档不能省
- 未登记的工具按 `forbid` 处理，默认值必须站在安全一边
- 审批提示要说清做什么、对谁做、能不能撤销
