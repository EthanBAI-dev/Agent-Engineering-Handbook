# Parallelization：互不依赖的步骤，没有理由排队

> 本课结果：你能把扇出扇入接对，并说出一个分支失败时整次运行会怎样。

## 只看一句话的话

三个互不依赖的查询串行做是三份等待叠加，并行做是一份。

> **术语说明**
>
> - **扇出（fan-out）**：从一个节点同时分出多条分支。
> - **扇入（fan-in）**：多条分支汇合到同一个节点。

## 接法只有两行差别

```python
# 串行：一个接一个
graph.add_edge(START, "网页搜索")
graph.add_edge("网页搜索", "内部文档")
graph.add_edge("内部文档", "数据库")
graph.add_edge("数据库", "summarize")

# 并行：都从 START 出发，都汇到 summarize
for name in SOURCES:
    graph.add_edge(START, name)
    graph.add_edge(name, "summarize")
```

三个来源各花 0.3 秒，本机实测：

```text
=== 串行 ===
  耗时 0.91 秒
=== 并行 ===
  耗时 0.31 秒
```

扇入节点会等**所有**分支都完成才执行——这是 LangGraph 帮你做的，不用自己写等待逻辑。

## 汇总字段必须有 reducer

三个分支同时写 `findings`，所以它必须带合并规则：

```python
findings: Annotated[list[str], operator.add]
```

不加的话就是第 13 课那个 `InvalidUpdateError`。这不是意外，是并行场景下 reducer 从「可选」变成「必须」的那一刻。

## 顺序不要依赖

实跑里并行的结果顺序是：

```text
内部文档 → 数据库 → 网页搜索
```

而节点是按「网页搜索、内部文档、数据库」加进去的。**顺序对不上，而且不保证在别的版本、别的机器上一致。**

要知道每条结果来自哪里，就把来源写进数据本身：

```python
return {"findings": [f"{name} 找到了关于「{state['query']}」的资料"]}
```

靠位置推断来源，是并行代码里最常见的隐藏 bug。

## 一个分支失败，整次运行就失败

默认行为很干脆：

```text
整次运行失败：内部文档服务挂了
```

三个来源里挂了一个，另外两个查到的东西也拿不到了。

这在某些场景是对的（三份数据缺一不可），但更多时候你想要「尽力而为」：能查到几个算几个。

## 尽力而为：让分支自己兜住失败

```python
def source(state):
    try:
        ...
        return {"findings": [f"{name}：查到了"]}
    except ConnectionError as error:
        return {"findings": [f"{name}：查询失败（{error}）"]}
```

实跑结果：

```text
内部文档：查询失败（服务没响应）
网页搜索：查到了
综合 2 个来源得出结论
```

跑完了，但请注意最后那句提醒：**要让后面的节点知道有一条是失败的**。

如果 `summarize` 把「查询失败」当成一条正常资料去总结，用户会得到一个看起来完整、实际上缺了一块的答案——而且没有任何迹象表明缺了什么。失败的结果要带上可识别的标记，让下游能区分。

> **术语说明｜尽力而为**
> 部分失败时仍然返回可用的部分，而不是整体失败。前提是调用方知道哪些部分缺了。

## 什么时候不该并行

- **步骤之间有依赖**：第二步要用第一步的结果，那它本来就不能并行
- **共同写一个覆盖型字段**：会直接报错，得先想清楚合并规则
- **外部服务有速率限制**：三个请求同时打过去，可能三个一起被限流，反而更慢
- **只有两步，每步很快**：并行的调度开销可能比省下的时间还多

## 互动实验：把六个步骤排进两层

网页实验给你六个步骤和它们之间的依赖关系，你把能并行的放进同一层。

```text
全串行      →  6 份等待
排成两层    →  2 份等待
排错依赖    →  第二层拿不到第一层的结果，报错
```

通过条件：得到最短的总耗时，并且没有把有依赖关系的步骤放进同一层。

## 本课挑战：这段并行为什么没有变快

```python
for name in SOURCES:
    graph.add_edge(START, name)

graph.add_edge("网页搜索", "内部文档")     # 多加的一条
graph.add_edge("内部文档", "数据库")       # 多加的一条
graph.add_edge("数据库", "summarize")
```

问题：扇出接了，但又在三个分支之间连了串行的边。

`内部文档` 现在有两个前置（START 和 网页搜索），它必须等网页搜索跑完。扇出被这几条边抵消了。

**并行不是「从 START 连出去」就成立的，还要保证分支之间没有边。**

## 三个常见误区

### 「并行一定更快」

调度有开销，外部服务有限流。步骤很快或者对方限流时，并行可能更慢。先测再定。

### 「结果顺序和加节点的顺序一样」

实跑已经证明不一样。把来源写进数据，不要靠位置。

### 「一个分支失败没关系，其他的还在」

默认情况下整次运行都会失败。要「尽力而为」必须自己在分支里兜住，并且让下游能识别哪条失败了。

## 本课带走三句话

- 扇出扇入只是连线方式，扇入会自动等所有分支完成
- 汇总字段必须有 reducer，顺序不要依赖，来源写进数据里
- 默认一个分支失败就整体失败，尽力而为要自己兜
