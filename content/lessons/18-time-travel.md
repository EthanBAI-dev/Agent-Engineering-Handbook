# Time Travel：回到旧状态，再走一遍另一条路

> 本课结果：你能列出一次运行的全部快照，从中间任意一步重放，并改一个值分叉出另一条路径。

## 只看一句话的话

checkpointer 存下的不是最后一个状态，是每一步的状态——所以每一步都能回去。

> **术语说明**
>
> - **重放（replay）**：从某个旧快照原样再跑一遍。
> - **分叉（fork）**：从某个旧快照改一个值再跑，得到另一条路径。

第 03 课把 checkpoint 当成「会话记忆」，那只用到了它一半的能力。

## 每一步都存着

一次两个节点的运行，实跑结果是四个快照：

```text
共 4 个快照，从新到旧：
  下一步=('<已结束>',)   values={'budget': 3000, 'picked': '基础版', 'note': '预算 3000 元，最终选择 基础版'}
  下一步=('confirm',)   values={'budget': 3000, 'picked': '基础版', 'note': ''}
  下一步=('pick',)      values={'budget': 3000, 'picked': '', 'note': ''}
  下一步=('__start__',) values={}
```

`get_state_history` 从新到旧返回。每个快照带两样东西：当时的 `values`，以及**下一步该跑哪个节点**。

第二样才是关键。它意味着这个快照不只是一份数据备份，而是一个**可以继续执行的位置**。

## 重放：同样的输入，是不是真的给出同样的输出

```python
before_confirm = [h for h in history if h.next == ("confirm",)][0]
out = app.invoke(None, before_confirm.config)
```

`invoke` 的第一个参数是 `None`——不给新输入，从这个快照往下跑。

实跑结果：

```text
选中的快照：{'budget': 3000, 'picked': '基础版', 'note': ''}
重放结果：预算 3000 元，最终选择 基础版
```

输入没变，结果一样。这听起来是废话，但它正是重放的用途：**验证一段流程是不是确定性的**。

如果重放两次结果不同，说明这一步依赖了某些不在 State 里的东西——当前时间、随机数、外部服务的实时数据，或者一个 `temperature` 不为 0 的模型。这类隐藏依赖是 Agent 最难查的一类 bug，重放能把它们揪出来。

## 分叉：改一个值，得到另一条完整路径

```python
before_pick = [h for h in history if h.next == ("pick",)][0]
forked = app.update_state(before_pick.config, {"budget": 8000})
out = app.invoke(None, forked)
```

实跑结果：

```text
选中的快照：{'budget': 3000, 'picked': '', 'note': ''}
分叉结果：预算 8000 元，最终选择 豪华版
```

只改了一个输入，整条路径都变了：`pick` 重新判断，选了豪华版，`confirm` 也跟着变。

**原来那次运行仍然完好。**分叉之后这个 thread 有 9 个快照，两条分支都在。

## 这和第 17 课的区别

第 17 课已经用过一次分叉——退回 `propose` 之前改参数。区别在于目的：

| | 目的 | 谁在操作 |
| --- | --- | --- |
| 第 17 课 | 修正一个正在进行的任务 | 审批的人，在界面上 |
| 第 18 课 | 理解 Agent 为什么这样做 | 开发者，在调试时 |

同一个机制，两种用法。

## 用它来做什么

**调试。**Agent 在第 7 步选错了工具。传统做法是把整段对话重来一遍，祈祷它再错一次。有了时间旅行，第 6 步的状态就摆在那里，改条件直接重跑那一步。

**对比。**同一个起点分出两条路，看看换个提示词、换个模型、换个参数，结果差多少。第 27 课的评测会大量用到这个。

**回滚。**发现方向错了，退回更早的一步重新提案——第 17 课用的就是它。

## 一个前提和一个陷阱

**前提**是 checkpointer。没有它，「上一步」根本不存在。这已经是第四次提到这句话了，从第 03 课到这里，它一直是同一个地基。

**陷阱**是第 13 课那条：reducer 不能原地修改旧值。

```python
def merge(old: list, new: list) -> list:
    old.extend(new)      # 危险
    return old
```

原地修改会让 checkpoint 里保存的历史状态跟着变。等你想回到第 3 步时，会发现「第 3 步的状态」已经被第 7 步改掉了——时间旅行的地基被后来的运行悄悄挖空了。

正确写法是 `return old + new`：每次返回新对象，历史才是只读的。

## 互动实验：找出分岔点

网页实验给你一次「选错了方案」的运行，五个快照摆在时间轴上。你要：

```text
1. 找出哪一步是分岔点（哪一步之后结果就注定了）
2. 回到那一步之前，改一个值
3. 让它跑出另一个结果
```

通过条件：只改**一个**字段就让最终结果改变，并说出为什么改更靠后的快照没有用。

## 本课挑战：为什么这次分叉没有效果

```python
last = list(app.get_state_history(cfg))[0]      # 最新的快照
forked = app.update_state(last.config, {"budget": 8000})
out = app.invoke(None, forked)
```

问题：选的是**最后一个**快照，那时 `pick` 已经跑完了。

改 `budget` 不会让 `picked` 重新计算——这正是第 17 课那条规则：改字段不会重算依赖它的字段。而 `last.next` 是空的，图已经结束，也没有节点会再读这个新预算。

分叉必须回到**分岔点之前**，也就是那个「读取这个字段并据此做决定」的节点执行之前。

## 三个常见误区

### 「时间旅行会覆盖原来的运行」

不会。分叉创建的是新分支，旧快照仍然在。实跑里分叉之后快照从 4 个变成 9 个，两条路都保留着。

### 「重放结果不同，说明 LangGraph 不可靠」

正相反，说明你的图里有不在 State 里的隐藏依赖。重放是发现这个问题的工具，不是问题本身。

### 「有了时间旅行就不用写日志了」

快照记录的是 State，不是「为什么」。模型当时为什么选那个工具、外部服务返回了什么原始内容，仍然要靠第 27 课的可观测性手段记录。

## 本课带走三句话

- 快照带着「下一步跑哪个节点」，所以它是位置，不只是数据
- 重放用来验证确定性，分叉用来改一个变量看结果
- 分叉要回到分岔点之前，改后面的快照没有用
