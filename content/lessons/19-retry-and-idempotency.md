# Retry 与幂等：重试很容易，重试不重复扣款才难

> 本课结果：你能判断一个节点能不能安全重试，并给有副作用的步骤加上幂等键。

## 只看一句话的话

重试之前先问一句：这一步做第二次，外面看得见吗？

> **术语说明**
>
> - **重试（retry）**：节点失败后自动再跑一次。
> - **幂等（idempotent）**：同一个操作执行一次和执行多次，结果一样。
> - **幂等键**：标识「同一笔业务」的唯一值，通常是订单号或请求 id。

网络会抖，外部服务会返回 503。加重试是一行配置的事，难的是后面那一半。

## 加重试确实只要一行

```python
graph.add_node(
    "call_service",
    flaky,
    retry_policy=RetryPolicy(max_attempts=3, initial_interval=0.01, backoff_factor=1.0),
)
```

实跑结果：

```text
实际尝试 3 次 → 成功（第 3 次尝试）
```

前两次抛异常，第三次成功。调用方完全看不出中间失败过。

> **术语说明｜backoff_factor（退避系数）**
> 每次重试之间等待时间的放大倍数。真实项目里要设成大于 1，让重试逐渐拉开间隔，避免在服务已经过载时继续猛打。

## 重试不是万能的

次数用完，异常照样抛出来：

```text
重试 2 次后放弃：第 2 次：外部服务没响应
```

所以图里必须有一条失败路径。**不能假设重试总会成功**——外部服务可能宕机十分钟，你的三次重试全落在这十分钟里。

失败之后要做什么，取决于业务：转人工、记一条待办、返回一个「稍后再试」的回复。唯一不能做的是让异常直接冒到用户面前。

## 危险的那一半

现在把 `flaky` 换成一个真的会扣款的节点。失败点设在「扣款成功了，但回执没收到」——这是外部调用最常见的失败方式。

```python
def charge_unsafe(state: State) -> dict:
    ledger.append(state["order_id"])          # 副作用先发生
    if len(ledger) < 3:
        raise ConnectionError("扣款成功了，但回执没收到")
    return {"status": "已扣款"}
```

实跑结果：

```text
账本里现在有 3 笔：['o_3', 'o_3', 'o_3']
```

图报告「成功了」，用户被扣了三次。

**失败的是回执，不是扣款。**重试机制无法区分这两种情况——它只知道节点抛了异常，不知道异常抛出之前已经发生了什么。

## 幂等键：同一个 key 只生效一次

修法不在重试这一侧，在副作用这一侧：

```python
def charge_safe(state: State) -> dict:
    key = state["order_id"]                    # 幂等键：同一笔业务永远同一个 key
    if key in safe_ledger:
        return {"status": "已存在，直接返回上次结果"}
    safe_ledger[key] = "charged"
    ...
```

实跑结果：

```text
节点被调用 2 次，账本里只有 1 笔：{'o_4': 'charged'}
最终状态：已存在，直接返回上次结果（第 2 次调用）
```

节点跑了两次，钱只扣了一次。第二次进来时它发现这个 key 已经处理过，直接返回上次的结果。

关键在于**幂等键必须来自业务，不能是随机生成的**。用 `uuid4()` 当 key，每次重试都会得到一个新 key，等于没做。正确的来源是订单号、请求 id、消息 id 这类「同一笔业务永远相同」的值。

> **形式**：对照时序图 · `assets/lessons/19-retry-side-effect.svg`
> **画什么**：上栏无幂等键——三次尝试，账本里三条记录，右侧标「图报告成功」；
> 下栏有幂等键——同样三次尝试，账本只有一条，第二三次命中「已存在，直接返回」。

> **替代文本**：没有幂等键时重试会重复产生副作用，加上幂等键后同一笔业务只生效一次。

## 判断一个节点能不能安全重试

| 动作 | 能否重试 | 原因 |
| --- | --- | --- |
| 读文件、查数据库、算数 | 可以直接重试 | 没有副作用，跑一百次结果一样 |
| 写文件到固定路径 | 可以直接重试 | 覆盖写本身就是幂等的 |
| 扣款、发邮件、发消息 | 必须先加幂等键 | 重试等于再做一次，用户能看见 |
| 追加一行日志 | 看情况 | 重复的日志无害，但会干扰统计 |

注意第二行和第四行的对比：同样是写，**覆盖写天然幂等，追加写不是**。这条区别在设计工具时很有用——能用覆盖表达的操作，就别设计成追加。

## 把节点拆小，缩短危险区间

还有一个结构上的办法：把「产生副作用」和「记录结果」拆成两个节点。

```text
一个大节点：  扣款 + 更新订单状态 + 发通知     ← 失败点可能在任意位置
拆成三个：    扣款 → 更新状态 → 发通知         ← 每个都能单独重试
```

拆开之后，重试的粒度更细，而且 checkpointer 会在每个节点之后存一次——失败时能从最近的那一步恢复，不用把前面已经成功的部分重做。

这也呼应第 01 课那句「把节点写小」：当时的理由是好调试，现在多了一个理由是**好恢复**。

## 互动实验：让重试变安全

失败 2 次 + 有幂等键   →  账本 1 笔

## 本课挑战：这个幂等键为什么无效

```python
def send_email(state):
    key = f"{state['to']}_{datetime.now().isoformat()}"
    if key in sent:
        return {"status": "已发送过"}
    sent[key] = True
    mail_api.send(state["to"], state["body"])
    return {"status": "已发送"}
```

问题：key 里含有当前时间。

每次重试都是一个新的时间戳，因此永远命中不了「已发送过」这个分支。邮件会照发不误。

幂等键必须由**业务标识**构成：收件人 + 这封邮件对应的业务 id，而不是「什么时候发的」。

## 三个常见误区

### 「加了重试就更可靠了」

对无副作用的节点是。对有副作用的节点，重试把「一次失败」放大成了「多次执行」——实跑里三笔扣款就是这么来的。

### 「幂等键随便生成一个唯一值就行」

「唯一」不是要求，「同一笔业务永远相同」才是。随机值和时间戳都满足唯一，但都无效。

### 「重试次数调大一点就不用管失败路径了」

外部服务可能宕机很久。次数再大也有用完的时候，失败路径是必须存在的，不是可选项。

## 本课带走三句话

- 重试之前先问「这一步做第二次，外面看得见吗」
- 幂等键要来自业务标识，随机值和时间戳都等于没做
- 重试次数总会用完，失败路径是必须品
