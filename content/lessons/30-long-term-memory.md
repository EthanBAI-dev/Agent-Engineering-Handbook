# 长期记忆与毕业项目：记住这个人，而不只是这段对话

> 本课结果：你能让 Agent 跨会话记住用户的事实，跨用户彻底隔离，并交付一个通过验收的毕业项目。

## 只看一句话的话

thread 记的是「这段对话说了什么」，长期记忆记的是「这个人是谁」——两者存在不同的地方。

> **术语说明**
>
> - **store（长期存储）**：按用户保存的事实，跨所有会话可见。
> - **命名空间（namespace）**：给存储分区的路径，本课用它做用户隔离。

第 03、15 课的记忆都绑在 thread 上，换个会话就从头开始。但用户不会觉得「换了个会话」是重新认识一次的理由。

## 三层记忆，分别管什么

| 管什么 | 谁负责 | 哪一课 | 生命周期 |
| --- | --- | --- | --- |
| 这一次调用带上哪些消息 | 上下文管理 | 第 14 课 | 跑完就不管了 |
| 这段对话说了什么 | checkpointer | 第 03、15 课 | 按 thread 存，会话结束仍在 |
| 这个人是谁 | store | 本课 | 按 user 存，跨所有会话 |

三层不是替代关系，是叠加。**大多数「Agent 忘了」的抱怨，先要判断问的是哪一层。**

## 接上 store 只多一个参数

```python
app = graph.compile(checkpointer=InMemorySaver(), store=store)
```

节点通过参数拿到它：

```python
def recall(state, config, *, store: BaseStore) -> dict:
    user_id = config["configurable"]["user_id"]
    items = store.search(memory_ns(user_id))
    ...
```

注意 `user_id` 和 `thread_id` 一样，放在 `configurable` 里——它是**运行配置**，不是 State 字段。第 29 课那条仍然成立：它必须由服务端填，不能由客户端提供。

## 命名空间带上 user_id

```python
def memory_ns(user_id: str) -> tuple[str, ...]:
    return ("users", user_id, "memories")
```

这一行做了两件事，**都不是可选项**：

1. **隔离**：bob 搜不到 alice 的命名空间
2. **删除**：用户要求删除数据时，删掉一个前缀就够了

第二件是法律要求。混在一起存，你永远说不清删干净了没有。

## 回忆 → 回答 → 记住

```text
START → recall → respond → remember → END
```

实跑结果：

```text
=== 1. 第一段会话：什么都不知道，然后学到两件事 ===
alice 在 t1 说：我在学 LangGraph，顺便说我喜欢咖啡
  [recall] 关于 alice 已知 0 条：[]
  → （我还不了解你）

=== 2. 换一个 thread：会话历史没了，但人还记得 ===
alice 在 t2 说：还记得我吗
  [recall] 关于 alice 已知 2 条：['喜欢咖啡', '在学 LangGraph']
  → （我记得：喜欢咖啡、在学 LangGraph）
```

这就是和第 03 课的区别：thread 换了，checkpoint 是空的，但 store 里关于 alice 的事实还在。

## 跨用户：一条都不该看见

```text
=== 3. 换一个用户 ===
bob 在 t3 说：还记得我吗
  [recall] 关于 bob 已知 0 条：[]
  → （我还不了解你）
```

这是第 29 课那条隔离，在长期记忆这一层的落法。

## 同一条事实说三次，只存一条

```python
store.put(memory_ns(user_id), fact, {"fact": fact})   # key 用事实本身
```

实跑结果：

```text
alice 的长期记忆共 2 条：['喜欢咖啡', '在学 LangGraph']
```

说了三次咖啡，只存一条。key 用事实本身，重复写入就是覆盖——**这是第 19 课的幂等换了个场景**。

如果 key 用时间戳或随机 id，记忆库会被同一件事塞满，检索时还要去重。

## 最难的不是存，是判断

存一条事实是一行代码。难的是这三个问题：

**什么值得记？**把每句话都记下来，等于没记——检索时全是噪声。通常只记「稳定的、会影响以后回答的」事实：偏好、身份、长期目标。一次性的信息（这次要查的订单号）不该进长期记忆。

**记错了怎么办？**用户换了口味，旧事实要能被覆盖或删除。这意味着提取事实时要考虑「它和已有的哪一条冲突」，而不只是往里加。

**用户要求删除时，你知道该删哪些吗？**命名空间设计决定了这一步做不做得到。

真实项目里，「什么值得记」通常交给模型判断——那就是又一次模型调用，也就是又一个会出错的地方，还要算进第 10 课的预算。**先用规则能解决的部分，剩下的再交给模型。**

## 互动实验：三层记忆各管一段

网页实验给你同一个用户的三段对话，你判断每次「它记不记得」由哪一层决定：

```text
同一段对话里的上一句     →  这次调用带上了吗（第 14 课）
换个会话后的上一次对话   →  checkpoint 在不在（第 03、15 课）
换个会话后的用户偏好     →  store 里有没有（本课）
```

通过条件：三种「忘了」都能指出病因在哪一层，并说出各自的修法不同在哪。

## 毕业项目

把三十课装成一个你自己要用的 Agent，并交付**验收记录**，不是「它能跑」。

### 必须具备

| 能力 | 来自 | 验收方式 |
| --- | --- | --- |
| 一张能循环的图 | 01、02 | 单步执行能说清每一步改了什么 |
| 会话记忆，进程重启后还在 | 03、15 | 重启进程后接着上次继续 |
| 危险操作前人工审批 | 04、16 | 批准和拒绝各跑一次 |
| 单次请求调用上限 | 10 | 失控请求被截断并给出说明 |
| 副作用幂等 | 19 | 重复提交只生效一次 |
| 输入与工具参数校验 | 11、28 | 越界参数被拒绝 |
| 用户隔离 | 29 | 两个账号读不到对方的数据 |
| 一个五条以上的数据集 | 27 | 能说出上次改动修好和弄坏了什么 |

### 验收记录长什么样

每条写清四栏，第四栏最常被漏掉：

```text
输入      ：固定的、可重复的
操作      ：包括人的回答
预期结果  ：状态里该有什么
外部断言  ：外部世界有没有发生变化
```

只检查返回值的验收，挡不住「说了没做」和「说没做却做了」。

### 明确写出还没做的部分

这一条和上面同样重要。第 20 课那张「教学版 vs 生产版」的表，你的项目也要有一张：还没做监控？没做备份？没做速率限制？写下来。

**知道自己缺什么的系统，比自以为完整的系统安全得多。**

## 本课挑战：这条记忆该不该存

```text
1. 「我叫小白」
2. 「帮我查一下订单 10086」
3. 「以后回复都简短一点」
4. 「今天心情不好」
```

参考答案：1 和 3 该存（身份、稳定的偏好）；2 不该（一次性信息，属于这段对话）；4 要看产品定位——存了可能贴心，也可能让用户觉得被监视。

**第 4 条没有标准答案，这正是重点：长期记忆的边界是产品决定，不是技术决定。**存之前先问一句：如果用户看到你记下了这条，他会觉得贴心还是不安？

## 三个常见误区

### 「长期记忆就是把对话历史全存下来」

那是 checkpointer 干的事。长期记忆存的是提炼过的事实，全存等于没提炼，检索时全是噪声。

### 「记得越多越好」

记忆会进每次调用的上下文，撞上第 14 课的预算。而且记错的事实会持续影响以后每一次回答，比不记更糟。

### 「删除功能以后再加」

命名空间设计决定了能不能删。事后再改存储结构，代价比一开始就按 user 分区高得多。

## 课程带走三句话

- 三层记忆管三件事：这次调用、这段对话、这个人
- 命名空间带上 user_id，隔离和删除都靠它
- 长期记忆最难的是判断什么值得记，不是怎么存

## 写在最后

三十课下来，真正反复出现的其实只有三条：

**State 是唯一的现场。**看不懂行为时，先看这一步的 State 里到底有什么——第 12 课的静默丢弃、第 03 课的 thread 隔离、第 26 课的检索落空，查起来都是同一个动作。

**代码是约束，提示词是建议。**风险分级、工具清单、参数校验、调用上限、拒绝路径——凡是不能失效的，都要写成代码。

**能跑不等于能用。**拒绝路径、失败路径、越权路径不会在正常使用中暴露，只会在事故里暴露。所以每一课都在问同一个问题：**你怎么证明它？**

祝你做出真正能用的东西。
