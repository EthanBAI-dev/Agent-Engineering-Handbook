# 零基础读者规则（最高优先级）

本文件是本 skill 的核心约束。任何与它冲突的写作习惯都以本文件为准。

---

## 0. 读者画像

请假设读者：

1. 没写过代码，没用过命令行。
2. 不认识「状态、节点、边、归并器、存档器、中断、子图、上下文、词元、工具调用」这类词。
3. 只具备普通高中水平的常识。
4. 阅读是为了建立直观理解，不是为了读文档。
5. 连续遇到多个陌生术语时，很可能直接关掉页面。

**不要默认读者读过上一讲。** 每一讲都必须能独立读懂——
承接上一讲的问题可以，但那个问题必须在本讲的导读里重新说清楚，不能只写「接上一讲」。

---

## 1. 术语准入机制

任何专业术语进入正文前，必须通过五项检查：

1. 这个词是否是理解当前内容所必需的？
2. 是否可以先用普通语言说明，再给出专业名称？
3. 是否能用具体场景、动作或生活现象解释？
4. 对这个术语的解释是否又引入了新的陌生术语？
5. 如果删除这个词，是否影响读者理解核心内容？

### 引入顺序

**具体场景 → 日常解释 → 专业名称 → 简单例子**

绝对不能是：**专业名称 → 用更多专业名称去解释**。

错误示例：

> 状态是图中所有节点共享的数据结构，由 schema 定义。

它确实「解释」了状态，但解释里又出现了图、节点、共享、数据结构、schema 五个新词。

正确示例：

> 一整张流程从头到尾只有一份数据，每一步都能看它、改它，改完下一步就读到改过的。
> 这份数据有个名字，叫状态。

### 三条硬约束

- 解释一个专业词时，不得使用尚未解释过的专业词。
- 同一段原则上只引入一个新的核心概念。
- 一段中如果出现三个及以上读者不熟悉的专业词，必须拆分或重写。

### 英文 API 名的特殊处理

`StateGraph`、`add_messages`、`invoke` 这类英文名**可以出现**，
但必须紧跟一句中文说明它干什么。它们不算「术语」，算「命令的名字」——
就像读者不需要理解 `cd` 这个缩写的来历，只需要知道它是「进入某个文件夹」。

## 2. 文章开头规则

开头的任务不是展示专业性，而是让读者知道三件事：

1. 这一讲讨论的是什么现实问题；
2. 这个问题和上一讲留下的困难是什么关系；
3. 读完以后能够理解什么。

**开头前两段不得出现未经解释的专业术语。**

标题下放一段**两到三句、约 60 到 120 个汉字**的导读，
依次交代「现实问题是什么 — 会经过哪些核心概念 — 读完能判断什么」。

导读可以把技术词当路标提前亮出，但不在这里密集下定义；
正文第一次真正使用时仍要按「日常解释在前、专业名称在后」的顺序引入。

**导读只介绍内容，不介绍文章的内部结构。** 不写「本讲分三部分」
「先看直观部分，再看深入部分」这类阅读说明。

禁止的开头方式：

- 直接给出专业定义
- 连续罗列专业名词
- 使用「众所周知」
- 默认读者已经读过上一讲
- 一上来就贴代码

推荐的开头方式：

- 一个具体的问题
- 一个读者可能见过的现象
- 一个简单的对比
- 一个容易想象的小实验

在引入任何专业词之前，先回答：「这个东西在现实中是用来做什么的？」

---

## 3. 专业词密度检查

逐段检查。一段中出现三个及以上目标读者不熟悉的专业词，必须执行下列操作之一：

1. 删除不必要的专业词；
2. 把一段拆成多段；
3. 先用日常表达解释，再补充专业名称；
4. 增加一个具体例子；
5. 把次要概念移到本讲靠后位置，或按归属表移到后面的讲次。

对每一段标记：本段新引入了哪些概念、哪些词可能让零基础读者困惑、
理解本段需要哪些前置知识、是否存在「用陌生词解释陌生词」。

机器辅助：

```bash
node .claude/skills/langgraph-course-lesson/scripts/check-readability.mjs <文件或目录>
```

它会给出首次出现位置、开头违规、每段密度和「用陌生词解释陌生词」的候选清单。
**它只是筛子，不能替代人工判断。ERROR 必须清零，WARN 必须逐条给出保留理由。**

## 4. 零基础读者模拟

以一名没写过代码的普通读者身份，逐段阅读，每段回答七个问题：

1. 我是否知道这一段在说什么？
2. 是否出现我不认识的词？
3. 作者是否在解释之前就使用了专业词？
4. 这一段与上一段是什么关系？
5. 我能否用自己的话复述这一段？
6. 我是否知道这个知识在现实中有什么用途？
7. 我是否愿意继续阅读下一段？

任何一项为否，标记该段需要修改，并说明处理方式：
增加场景 / 增加例子 / 解释术语 / 删除术语 / 拆分句子 / 减少信息 / 补充过渡 / 调整顺序。

**明确指出读者最可能在哪一段关掉页面。**

---

## 5. 语言风格

- 像一位耐心的老师面对第一次接触编程的学生，不像工程师给同事写文档。
- 能用普通语言表达的内容，不要故意换成专业术语。
- 优先使用「程序」「你写的代码」「那份共享数据」这类直观表达；
  确实需要时才逐步引入「节点」「状态」「归并器」。
- **不要把程序写成人。**「agent 自己思考下一步」要改成
  「程序把当前对话发给模型，模型回一个『要调哪个工具』」。
  唯一例外是模型本身的输出，那可以说「模型判断」。
- 每个比喻都要说明它是比喻；当边界重要时，说明它在哪里不成立。

---

## 6. 简化不等于降低准确性

零基础不是含糊的借口。可以先说「它会一直转到很多步之后才报错停下」，
再顺着补一句「本机实测这个上限是 10007 步，不同版本不一样，调试时把它改成 5 就能几秒看出来」。

先给直觉，再给条件，两者都要有。**绝不允许为了顺口而写出会误导读者的句子。**

特别注意分清两类不确定性：

- **框架行为是确定的**——同样的图、同样的输入，跑多少次结果都一样。
- **模型行为是不确定的**——同一个问题，模型这次调两个工具，下次可能只调一个。

**凡是依赖模型输出的例子，必须写明「你跑出来可能不一样」。**

---

## 7. 输出后的自查清单

输出最终文章后，必须额外列出：

- 本讲保留了哪些专业词
- 为什么必须保留这些词
- 每个词第一次出现时是如何解释的
- 哪些专业词因不影响主线而被删除或后移
- 哪些段落对零基础读者仍可能偏难

这份清单只写在审校报告里，不写进正式正文。
**术语应在第一次出现的位置自然解释，不依赖文末速查表补救。**

---

## 8. 最简单的三问判断法

检查任意一段时，只问三个问题：

1. 第一句话里有没有未经解释的专业词？
2. 解释一个陌生词时，是否又使用了更多陌生词？
3. 读者能不能把这段内容想象成一个具体画面？

任何一个答案不理想，这一段就还不是零基础教程。
